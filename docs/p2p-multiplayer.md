# 元气骑士·深渊回响 — P2P 联机方案（草案）

> 状态：**方案文档**（本期不实现）。目标：为单机版增加 2~4 人 P2P 联机，不引入服务器成本、不引入构建工具、保持"双击 index.html 即可玩"的零依赖特性。

---

## 1. 技术选型

| 项 | 选择 | 理由 |
|---|---|---|
| 传输 | **WebRTC DataChannel**（浏览器原生 P2P） | 零插件、零服务器转发数据、低延迟（UDP 语义）、Chrome/Edge/Firefox 全支持 |
| 信令 | **双方案**：① 手动复制邀请码（无服务器）；② 可选公共 WebSocket 信令（跨网） | 局域网/同机测试零依赖；跨网时信令只交换 SDP/ICE，不转发游戏数据 |
| 权威 | **主机权威（Host-authoritative）** | 地牢生成、敌人 AI、掉落判定全部在主机运行，客机只发输入，杜绝作弊与不同步 |
| 同步频率 | 状态快照 20Hz + 输入 30Hz | 平衡带宽与延迟 |

### 信令方案 A：手动邀请码（零服务器）
1. 主机点击"创建房间" → 生成 Offer SDP → 显示为一段可复制的文本（含 ICE candidates）
2. 客机点击"加入房间" → 粘贴主机邀请码 → 生成 Answer SDP → 复制回传给主机
3. 主机粘贴 Answer → DataChannel 建立
> 适合：同一局域网、同一台电脑开两个浏览器窗口、远程桌面协作。

### 信令方案 B：公共 WebSocket 信令（跨网，可选）
- 一个极简信令服务器（Node.js，约 100 行）：只做房间码 ↔ SDP/ICE 转发，不碰游戏数据
- 房间码 6 位（如 AB12CD），主机创建、客机输入房间码加入
- 部署：任意免费 Node 托管（Render/Railway/Cloudflare Workers）

## 2. 架构

```
┌─────────────┐   DataChannel(二进制)   ┌─────────────┐
│   主机 Host   │ ◄──────────────────────► │   客机 Client │
│ 权威模拟+地牢  │   输入(30Hz) / 快照(20Hz) │  本地预测+插值 │
└─────────────┘                          └─────────────┘
```

- **主机**：运行完整游戏模拟（现有 Game.update 不变），额外维护 net 模块：收集客机输入 → 应用到对应客机玩家 → 广播状态快照
- **客机**：运行"渲染 + 输入采集 + 预测"的轻量客户端：本地模拟自己的移动/射击（预测），收到快照后校正；其他玩家/敌人/子弹用快照插值渲染
- **大厅组队**：大厅（N3 已实现）中增加"创建房间/加入房间"入口，房主选英雄后传送门开局，客机同步进入

---

## 3. 同步协议（二进制，非 JSON）

| 消息 | 方向 | 内容 | 频率 |
|---|---|---|---|
| INPUT | 客→主 | 移动向量、瞄准角、按键位图（攻击/技能/大招/翻滚/切枪/互动） | 30Hz |
| SNAP | 主→客 | 全量快照：玩家们（位置/血量/能量/武器/朝向）、敌人（位置/血量/阶段/状态）、子弹（位置/速度/类型）、掉落物、门/房间状态 | 20Hz |
| EVENT | 主→客 | 一次性事件：伤害数字、音效、粒子、toast、宝箱开启、合成结果 | 事件驱动 |
| SYNC | 双向 | 握手、英雄选择、房间码、断线重连 | 低频 |

**快照压缩**：坐标用 16bit 定点数（±4096 范围，精度 0.125px）；敌人只同步"可见/活跃"子集；子弹用增量（只同步新生成与销毁的）。

---

## 4. 延迟处理

| 问题 | 方案 |
|---|---|
| 客机操作延迟 | **输入预测**：客机本地立即执行自己的移动/射击（复用现有 Player.update），快照到达后只校正偏差 > 阈值（如 2px）的实体 |
| 敌人/其他玩家抖动 | **插值**：渲染位置 = 上一快照与当前快照之间按时间插值（100ms 缓冲） |
| 击杀判定 | 以主机为准：客机看到"打中"只是表现，实际伤害由主机结算后通过 EVENT 广播伤害数字 |
| 高延迟（>300ms） | 自动降级：客机关闭预测，纯快照渲染；提示"网络延迟高" |

---

## 5. 断线与重连

- **客机掉线**：主机保留其玩家 10 秒（原地不动、无敌），期间可重连（携带会话 token 恢复）
- **主机掉线**：若客机数 ≥ 2，选举延迟最低的客机为新主机（新主机从最近快照继续模拟，地牢状态以新主机为准）；若只有 1 名客机，直接判负回大厅
- **重连**：新客机加入时，主机发送全量 SNAP + 地牢种子（Dungeon.generate 支持固定随机种子的话，可本地重建地图）

## 6. 与现有代码的集成点

| 现有模块 | 改动 |
|---|---|
| js/lobby.js | 大厅增加"创建房间/加入房间"UI 与房间码输入 |
| js/game.js | Game.update 增加 net 分支：主机模式应用客机输入；客机模式跳过本地模拟、用快照驱动渲染 |
| js/entities.js | Player 增加 netId；客机玩家由快照驱动（Player.update 拆出"输入→动作"与"动作→状态"两段，客机只跑前者） |

| js/main.js | 联机菜单流程 |
| 新增 js/net.js | 信令封装、DataChannel 封装、快照编解码、预测/插值/校正 |

## 7. 分阶段实施路线

| 阶段 | 内容 | 验收 |
|---|---|---|
| P1 信令 | 手动邀请码 + DataChannel 建立 + 心跳 | 两个浏览器窗口能"连接" |
| P2 大厅组队 | 房间码、英雄选择同步、房主开局 | 双人进入同一地牢 |
| P3 战斗同步 | INPUT/SNAP/EVENT 全协议、预测+插值 | 双人同屏战斗，延迟 <150ms 时手感接近单机 |
| P4 完整玩法 | 掉落/宝箱/合成/任务/祝福同步、断线重连 | 双人通关 6 层 |
| P5 跨网 | 可选 WebSocket 信令服务器 | 公网联机 |

**本期范围**：仅 P1 之前的方案定稿（本文档）。P1 起需要单独排期，避免与单机功能开发互相干扰。

---

## 8. 风险与对策

| 风险 | 对策 |
|---|---|
| 浏览器 WebRTC 在 file:// 协议下的限制 | 联机模式要求通过 http:// 访问（本地 npx serve 或任意静态服务器）；单机模式不受影响 |
| 主机权威下客机"打空气"的体感 | 预测 + 客户端表现层（命中特效本地播放，伤害数字以 EVENT 为准） |
| 快照带宽 | 20Hz × 压缩快照 ≈ 5~15KB/s/人，4 人局 < 60KB/s，可接受 |
| 代码复杂度 | 严格隔离：net.js 不触碰单机逻辑；单机模式零改动 |
